About this document

Setup, the workflow inventory, the scope-out list, and the per-feature reasoning all live in README.md; this document focuses on three things the README does not go into: the state-machine architecture, how concurrency and bulk operations are kept honest, and where to look in the code.

How the project was built

Developed by orchestrating Claude Code as a multi-agent workflow. Source of truth lives in version-controlled docs (assignment/, docs/) and in a repo-level project constitution; per-role agents (backend, frontend, reviewer) under .claude/agents/ own scoped surfaces and hand off when a change crosses their boundary. Every state-machine or lifecycle slice goes through a reviewer pass — inline or spawned — before the PR is opened.

State machines

Two lifecycles run side-by-side. Approving a bill is the seam — that is the only place a Payment is created. From that point on, the bill and the payment evolve through their own transitions, with two cascades flowing between them.

Bill:    DRAFT ──submit──> PENDING_APPROVAL ──approve──> APPROVED
                                              └─reject──> REJECTED
         APPROVED ─(payment.schedule)──> SCHEDULED ─(payment.markPaid|release+mark)──> PAID
         APPROVED ─(payment.markPaid UNSCHEDULED, OFF_PLATFORM)─────────────────────> PAID
         any non-terminal ─(archive | payment.cancel cascade)──> ARCHIVED

Payment: UNSCHEDULED ──schedule──> SCHEDULED ──release──> INITIATED ──markPaid──> PAID
         UNSCHEDULED ──markPaid (OFF_PLATFORM)────────────────────────────────────> PAID
         FAILED ──retry──> SCHEDULED
         {UNSCHEDULED|SCHEDULED|INITIATED|FAILED} ──cancel──> CANCELED  (+ Bill→ARCHIVED)

The "cancel cascades the bill to ARCHIVED" rule encodes the one-Payment-per-Bill invariant: the system never re-creates a Payment, so a CANCELED payment leaves the bill with no forward motion — archiving makes the dead end honest in the audit trail.

Concurrency — transactions + CAS

Every state-changing service method opens a prisma.$transaction that reads the row → guards the status → writes the new row → writes the activity row. The activity log exists exactly when the parent write committed; the audit trail can never disagree with entity state. Two simultaneous transitions are caught by the status guard inside each transaction — the second one throws 409 *_INVALID_TRANSITION instead of silently overwriting.

How to verify Open two browser tabs as Admin, navigate both to the same DRAFT bill, hit Submit for approval in quick succession. One returns 200, the other surfaces an invalid-transition toast.

Bulk operations

Every toolbar action maps to a native bulk endpoint on the backend. There is no client-side fan-out — the frontend hooks are thin apiFetch wrappers around the bulk routes. Server-side, each endpoint delegates to a shared runBulk helper that loops the input ids and invokes the same single-item service method per id inside its own transaction. Three properties matter here:

  • Sequential, not Promise.all: deterministic activity-log ordering matters for an audit trail.
  • Per-item transaction: a failing row aborts only its transaction; siblings keep going. HTTP 200 always; partial failures appear inline.
  • Delegates to the single-item service: the state machine is implemented once, and any lifecycle change is automatically reflected in bulk.
How to verify Select a mix of DRAFT and PENDING_APPROVAL rows and hit Approve. The summary toast reports "X of Y succeeded · Z failed"; Details opens the per-item modal.
