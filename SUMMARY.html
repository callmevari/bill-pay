Architecture decisions worth flagging

Full rationale + tradeoffs in README.md → Architecture + data model decisions and docs/backend.md.

  • Bill and Payment are separate lifecycles. Approve creates the Payment in UNSCHEDULED. Exactly one Payment per Bill — cancel cascade-archives the Bill so a CANCELED payment never leaves a stuck APPROVED bill.
  • Post-payment field lock. Once a non-cancelled Payment exists, amount / currency / paymentMethod on the Bill freeze (409 BILL_FIELD_LOCKED_POST_PAYMENT). Memo / dates stay editable.
  • bill.amount may diverge from sum(lineItems.total) by design. Real AP invoices carry tax, fees, shipping outside the line items; bill.amount is the source of truth, the detail page surfaces the divergence in amber.

Lifecycles

Bill:    DRAFT ──submit──> PENDING_APPROVAL ──approve──> APPROVED
                                              └─reject──> REJECTED
         APPROVED ─(payment.schedule)──> SCHEDULED ─(payment.markPaid|release+mark)──> PAID
         APPROVED ─(payment.markPaid UNSCHEDULED, OFF_PLATFORM)─────────────────────> PAID
         any non-terminal ─(archive | payment.cancel cascade)──> ARCHIVED
         Terminal: PAID, REJECTED, ARCHIVED.

Payment: UNSCHEDULED ──schedule──> SCHEDULED ──release──> INITIATED ──markPaid──> PAID
         UNSCHEDULED ──markPaid (OFF_PLATFORM)────────────────────────────────────> PAID
         FAILED ──retry──> SCHEDULED
         {UNSCHEDULED|SCHEDULED|INITIATED|FAILED} ──cancel──> CANCELED  (+ Bill→ARCHIVED)
         Terminal: PAID, CANCELED.

Concurrency — Prisma transactions + CAS

Every state-changing service method opens a prisma.$transaction: read-current → guard status → write the row → write the activity row. Two consequences:

  1. The activity row exists exactly when the parent write committed. Audit log can never disagree with entity state.
  2. Concurrent transitions are caught. Two simultaneous approve calls both read PENDING. The first commits; the second's guard runs against the now-APPROVED row and throws 409 BILL_INVALID_TRANSITION — no silent overwrite.

Cascades follow the same shape: cancel + bill archive + both activity rows commit together in backend/src/payments/payments.service.ts.

How to verify Open two browser tabs as Admin, navigate both to the same DRAFT bill, hit Submit for approval in quick succession. One returns 200, the other surfaces a BILL_INVALID_TRANSITION toast.

Bulk operations

Every toolbar action maps 1:1 to a native bulk endpoint: bills (approve, archive, edit, submit-for-approval, reject) and payments (release, mark-as-paid, cancel, schedule, retry). Frontend hooks are thin apiFetch wrappers — no client-side fan-out.

Server-side, each endpoint delegates to a shared runBulk helper (backend/src/common/bulk/bulk-runner.ts) that loops ids, invokes the single-item service method per id in its own prisma.$transaction, and returns { results, summary }.

  • Sequential, not Promise.all. Deterministic activity-log ordering matters for the audit trail.
  • Per-item transaction. A failing row aborts only its transaction; siblings keep going. HTTP 200 always; partial failures appear inline.
  • Delegates to the single-item method. State machine implemented once. Lifecycle changes propagate to bulk automatically.
How to verify On the bills index, select a mix of DRAFT and PENDING_APPROVAL rows, hit Approve. The summary toast says "X of Y succeeded · Z failed"; Details opens the per-item modal.

Testing

Two layers with non-overlapping jobs (recipe in CLAUDE.md → Testing and docs/backend.md → Testing strategy):

  • Unit (mocked Prisma) — decisions in code: parsers, guards, mappers, error translation. pnpm --filter backend test → 73 / 73. pnpm --filter frontend test → 10 / 10.
  • E2E (real Postgres, isolated test_e2e schema, reset + reseed per test) — persistence, transactional atomicity, FK translation, role guard end-to-end. pnpm --filter backend test:e2e → 76 / 76.
